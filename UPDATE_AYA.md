# Обновление AYA — первый этап

Основа: GitHub-архив коммита 01068b9be84a15267801f0d825acaeeefc732289.
Этот архив содержит исправленный код Django. Новый дизайн главной и рейтинг в этот этап не входят.

## Что исправлено

- В модели User восстановлены существующие в базе поля срока статуса «Новый волонтёр», даты и автора выдачи доступа.
- Новая миграция events/0010_normalize_eventhero_constraint.py устраняет два одноимённых ограничения EventHero и оставляет одно. Старые миграции не изменены.
- Одобрение заявки оставляет кандидата 0/3. Третий визит или ручная выдача доступа записывают дату и автора; новый волонтёр получает отметку на 14 дней. Повторная выдача доступа не сбрасывает дату. Старому волонтёру отметка не назначается.
- История визитов видна владельцу после получения доступа. В панели есть недавно одобренные за 14 дней; отметка нового волонтёра отображается в профиле и карточке списка.
- Модератор может отмечать визиты и исправлять отметки действующих кандидатов, но не одобрять/отклонять заявки, выдавать полный доступ, редактировать чужие профили, создавать/редактировать/удалять мероприятия и отчёты. История визитов после выдачи доступа защищена от удаления; пересмотр уже выданного допуска требует отдельного решения.
- Обычное участие модератора с полным доступом сохранено. Его права как участника и включение в статистику ранее не были окончательно определены.
- Редактирование ролей проверяет и текущую, и назначаемую роль относительно прав редактора.
- Запись и отмена участия работают только через POST с CSRF. Повторный запрос записи не отменяет участие. Учитываются публикация, завершение, время окончания и лимит мест. SQLite использует IMMEDIATE-транзакции для последовательной обработки конкурирующих изменений.
- Герои и оцениваемые — только участники события. Оценки сохраняются после завершения мероприятия. Отмена участия с уже внесённой ролью или оценкой требует обращения к организатору, чтобы не оставлять отчёт без участника.
- Гостям доступна страница публичного одобренного события; черновики не открываются обычным пользователям. Кандидаты не видят список участников и не могут записаться.
- Ссылки возврата после действий проверяются, чтобы не перенаправлять пользователя на посторонний сайт.

## Как обновить GitHub

1. Сделайте копию вашей локальной папки проекта.
2. Скопируйте содержимое папки aya-platform-fixed поверх файлов репозитория, где лежит manage.py. Не создавайте внутри репозитория ещё одну вложенную папку проекта.
3. Если настройки PythonAnywhere или локальные настройки менялись отдельно, сохраните их значения: SECRET_KEY, DEBUG, ALLOWED_HOSTS, пути базы и media. В DATABASES['default'] добавлено OPTIONS = {'transaction_mode': 'IMMEDIATE', 'timeout': 20}; сохраните эту настройку SQLite. Не публикуйте секретные значения в GitHub.
4. Добавьте новые файлы, включая users/services.py и events/migrations/0010_normalize_eventhero_constraint.py. Старые миграции оставьте на месте.
5. Проверьте список изменений и отправьте код в GitHub привычным способом. db.sqlite3 и media не добавляйте.

## Как обновить PythonAnywhere

Обновляйте в короткое окно без работы пользователей. Используйте ту же виртуальную среду Python, которая настроена для сайта. База на сервере должна оставаться рабочей базой; не заменяйте её приложенной ранее копией или тестовой базой.

В Bash-консоли:

```bash
cd /home/AYA1/mysite
```

Сначала создайте согласованную резервную копию SQLite вне репозитория:

```bash
python - <<'PY'
import sqlite3
from pathlib import Path
from datetime import datetime
backup_dir = Path('/home/AYA1/aya_backups')
backup_dir.mkdir(exist_ok=True)
backup_path = backup_dir / ('db_before_update_' + datetime.now().strftime('%Y%m%d_%H%M%S') + '.sqlite3')
with sqlite3.connect('db.sqlite3') as source:
    with sqlite3.connect(backup_path) as target:
        source.backup(target)
print('Резервная копия:', backup_path)
PY
```

Сохраните также резервную копию media и текущих настроек. Затем:

```bash
git status --short
git pull --ff-only
python -m django --version
python manage.py check
python manage.py showmigrations users events
python manage.py migrate --plan
```

Код проверен с Django 5.2.7, указанным в requirements.txt. Если окружение отличается, приведите его к требованиям проекта перед обновлением.

Для предоставленной базы план содержит только новую events/0010 и отсутствующие users/0027_volunteervisit_comment_compat, users/0029_merge_20260310_0510. Если они уже применены, соответствующих пунктов не будет. При неизвестных локальных миграциях, конфликте git pull, ошибке или неожиданном плане остановитесь и пришлите текст вывода. Не удаляйте миграции и не используйте --fake наугад.

Если план соответствует ожидаемому:

```bash
python manage.py migrate
python manage.py makemigrations --check --dry-run
python manage.py collectstatic --noinput
```

Последняя команда makemigrations здесь только проверяет согласованность: --dry-run не создаёт файлов. Обычный makemigrations без этих флагов на сервере не запускайте.

Откройте PythonAnywhere → Web → Reload.

## Проверка после Reload

- Вход, главная, список волонтёров и «О нас» открываются.
- Заявка одобряется старшей ролью в кандидата 0/3.
- Кандидат видит прогресс в своём профиле; не может записаться на мероприятие.
- Модератор видит панель визитов, не видит действий администратора и не может управлять событиями.
- Повторное посещение за день не создаётся; третий визит открывает доступ. Не создавайте фиктивные визиты реальным людям ради проверки.
- У нового волонтёра виден статус, у старого — нет; записаны дата и автор выдачи доступа.
- Повторная запись на событие не отменяет участие; при заполненных местах запись отклоняется.

Автоматические проверки на локальной копии проекта:

```bash
python manage.py test users.test_regressions --noinput
```

При проблемах не заменяйте базу сразу старой копией: после обновления могли появиться новые записи. Сохраните текущее состояние и текст ошибки, затем выбирайте восстановление с учётом новых данных.
