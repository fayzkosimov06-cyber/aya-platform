# AYA: диагностика и безопасное развёртывание

Инструмент aya_diagnose_profile.py читает текущую конфигурацию AYA и БД через Django. Он не сохраняет модели, не запускает HTTP views и не выводит значения контактов, дату рождения, пароли или токены. Проверка форм проводится на отсоединённой копии модели. Это проверено регрессионным тестом.

Запуск после подтверждённого доступа, только в окружении AYA:

```sh
cd /srv/aya
/srv/aya/venv/bin/python ops/aya_diagnose_profile.py --username azimus-asian --date 2026-09-29 --start 13:26 --end 13:39
```

Время: Asia/Dushanbe. Включается вся последняя минута 13:39; верхняя граница 13:40 исключается. Текущие значения могли измениться после ручного редактирования через Django Admin. Историческая запись action не доказывает, что форма сохранилась.

До любого развёртывания агент должен:

1. Проверить SSH host key по известному доверенному источнику, определить пользователя, реальный путь /srv/aya и состояние только aya.service.
2. Зафиксировать commit, ветку и локальные изменения VPS, не выводя environment или секреты.
3. Определить фактический backend БД и безопасную команду резервного копирования. Для SQLite — штатный backup и integrity_check копии. Для PostgreSQL — pg_dump нужной БД и проверка/пробное восстановление в отдельную БД AYA. Не использовать БД других проектов.
4. Создать закрытую резервную копию кода, конфигурации, БД и media AYA, проверить чтение архива и путь восстановления. Не выполнять reset --hard и не стирать неизвестные локальные изменения.
5. Сверить production с проверенным commit. Сохранить серверные настройки и секреты. settings.py из репозитория содержит настройки разработки; не заменять им production-конфигурацию. Отдельно включить password validators, если production их не задаёт.
6. Сначала проверить зависимости в отдельном окружении. Для этого обновления проверен официальный исходный код Django 5.2.18 (tag 5.2.18). Новые миграции не добавлены; существующие неприменённые миграции требуют отдельной проверки плана и обратимости.
7. Проверить Django check, migration plan и тесты. Собирать статику только AYA; не затрагивать общий Nginx и службы Telegram Archive. Перезапускать только aya.service после выполнения условий.
8. Проверить состояние aya.service и нужные HTTP страницы, ошибки в журналах AYA; для production не создавать тестовых реальных пользователей и не изменять аккаунт расследования. При ошибке откатить именно этот release по проверенному плану.

Путь SSH-ключа и known_hosts предоставляются через защищённые разрешения локального приложения, не через сообщения и не через Git. Требуются чтение/аутентификация GitHub и отдельное подтверждённое право записи для push. В этой сессии запись через подключённый GitHub connector не подтверждена (pull=true, push=false).

Оставшиеся проверки: фактические production DEBUG/SECRET_KEY, парольные валидаторы, TLS/cookies, защита от перебора, версии зависимостей, сохранность ротированных журналов за 29 сентября, точное содержание ранее добавленного тестового меню. Отсутствие подтверждения не означает наличие атаки.


Воспроизводимые тесты без production-конфигурации:

```sh
python manage.py test --settings=aya_platform.settings_audit --noinput
python manage.py check --settings=aya_platform.settings_audit
python manage.py makemigrations --check --dry-run --settings=aya_platform.settings_audit
```

Тестовая SQLite работает в памяти; файлы используют отдельную временную папку, почта — память процесса. Настройки production не импортируются. Для старых некорректных Instagram/LinkedIn неизменённые значения сохраняются как есть и не блокируют другие поля; новые некорректные значения запрещены, а построение ссылок независимо проверяет безопасность URL.
