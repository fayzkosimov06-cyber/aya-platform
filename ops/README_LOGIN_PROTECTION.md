# Защита входа AYA

Реализация: django-axes 8.3.1, штатный database handler и authentication backend перед сохранённым Django ModelBackend. Счётчики общие для всех Gunicorn-процессов, хранятся в SQLite AYA и не исчезают при смене cookies или перезапуске службы. Локальный cache не используется для ограничения.

Политика в `aya_platform/login_protection.py`:

- пять неудачных попыток вызывают временную паузу до 10 минут;
- учитываются логин в целом и сочетание логина с источником; отдельной блокировки всего IP нет;
- штатное окно django-axes очищает устаревшие счётчики, успешный вход сбрасывает ошибки;
- запросы во время паузы не продлевают её;
- разные страницы входа используют один счётчик: волонтёры, сотрудники, Django Admin и прямой вызов `authenticate(request=...)`;
- существующие сеансы, пароли, роли и признаки допуска не меняются;
- несуществующие логины получают ту же политику и сообщения;
- ни привилегированная роль, ни сеть не исключены из проверки.

Пауза обычно длится 10 минут от последней учитываемой ошибки. Если ошибки распределены между несколькими источниками/браузерами, часть старых записей может истечь раньше. Ответ вычисляет реальное время снятия ограничения по активным записям и возвращает HTTP 429 с `Retry-After`. HTML содержит таймер и возможность открыть чистую форму другого аккаунта. Клиентский JavaScript только показывает время; сервер проверяет ограничение самостоятельно. Пароль повторно не выводится и автоматически не отправляется.

Идентификатор нормализуется так же, как UsernameField Django (NFKC и пробелы по краям), с сохранением регистра. Реальная проверка пароля остаётся штатной Django. Источник извлекается из `REMOTE_ADDR`; `X-Real-IP` принимается только от 127.0.0.1/::1. На проверенном VPS AYA Gunicorn слушает только 127.0.0.1:8001, а собственный Nginx перезаписывает X-Real-IP значением remote_addr. Произвольный X-Forwarded-For не используется. Изменение этой топологии требует повторной проверки доверенных заголовков.

Пароли и перечисленные секретные поля маскируются перед служебной записью попыток. Секреты входа не передаются в журнал AYA: он получает только категорию результата, HTTP-статус и маршрут. Неуспешный ввод логина не приписывается владельцу этого логина как доказанное действие. Постоянный дополнительный журнал успешных входов django-axes выключен: существующий закрытый журнал AYA остаётся источником событий.

Миграции пакета создают новые `axes_*` таблицы. При первой установке его исторические RemoveField/RunPython относятся только к только что созданным пустым таблицам пакета. План не должен включать изменения существующих приложений AYA. Перед production проверить это на отдельной SQLite и сделать закрытую согласованную резервную копию БД, кода, настроек и media. После migrate сверить данные всех прежних таблиц; ожидаются только новые записи django_migrations, ContentType и стандартные разрешения нового приложения. Нельзя удалять старые пользовательские записи ради установки.

Откат: вернуть предыдущий Git commit и запустить только aya.service. Пакет не меняет старые зависимости, а новые таблицы не мешают прежнему коду. Не удалять их и не заменять рабочую БД старой копией при обычном откате кода: это может потерять новые действия пользователей.

Для исключительного сброса паузы уполномоченным оператором существует штатная команда `manage.py axes_reset_username USERNAME` в production-окружении AYA. Это сбрасывает только счётчик входа, не меняет пароль, роль, активность и допуск. Массовый сброс для отладки на production не выполнять. Для обычного пользователя пауза снимается автоматически.

Проверки:

```sh
python manage.py test --settings=aya_platform.settings_audit --noinput
python manage.py check --settings=aya_platform.settings_audit
python manage.py makemigrations --check --dry-run --settings=aya_platform.settings_audit
```

Дополнительно на Linux проверяются независимые процессы, параллельные ошибочные попытки и сохранность старых данных при миграции на синтетической SQLite. Реальные аккаунты для активных тестов не используются. Одновременные запросы, уже прошедшие проверку до регистрации очередного отказа, могут завершиться; после фиксации порога последующие попытки отклоняются. Эта защита входа не заменяет защиту сервера от объёмного сетевого DDoS.

Источники: [документация django-axes](https://django-axes.readthedocs.io/en/latest/4_configuration.html), [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#login-throttling).
