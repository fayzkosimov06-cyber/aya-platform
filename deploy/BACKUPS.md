# Резервные копии AYA

`aya-backup.timer` запускает копирование ежедневно в 03:30–03:35 по Душанбе;
`Persistent=true` запускает пропущенное задание после включения сервера.
Копии находятся в `/home/deploy/aya-backups/daily` (каталог 0700, файлы 0600).
Хранятся последние 14 успешно проверенных копий. Ручные копии перед обновлениями
и незавершённые каталоги `.partial-*` автоматически не удаляются.

Каждая копия содержит SQLite (через SQLite backup API, включая committed WAL),
медиафайлы, закрытые материалы карт, отслеживаемый Git код, настройки AYA,
файл окружения AYA, её unit-файлы, номер commit и версии Python/пакетов.
Архивы не включают другие проекты и их настройки. Секреты остаются внутри
закрытой копии; не публикуйте архивы и `config.tar.gz`.

До признания копии готовой проверяются SHA-256 всех файлов, восстановление
базы в отдельный временный файл с `PRAGMA integrity_check` и извлечение каждого
архива в закрытый временный каталог. Ошибка проверки не удаляет старые копии.
Одновременные запуски блокируются. Исходная база открывается только для чтения.
При временной задержке чтения Git задание повторяет проверку метаданных один
раз; после повторного таймаута выводит название этапа и сохраняет прежние копии.
На работающем сайте база и файлы копируются последовательно, не как единый
мгновенный снимок диска. При изменении файла во время чтения задание прерывается.
Для точного состояния перед обновлением используется отдельная копия во время
короткой остановки только `aya.service`.

## Проверка работы

```sh
systemctl list-timers aya-backup.timer
systemctl status aya-backup.service
journalctl -u aya-backup.service --since '2 days ago'
```

Успешный запуск завершится с кодом 0 и строкой `"verified": true`.
Неуспешный запуск имеет статус failed; старые проверенные копии сохраняются.
При нехватке места копирование не начинается. Незавершённые копии после сбоя
нужно отдельно проверить и убрать вручную после выяснения причины.
Повторная проверка: с production-окружением выполните
`/srv/aya/venv/bin/python /srv/aya/manage.py backup_aya --verify ПУТЬ_КОПИИ`.

## Восстановление

Сначала проверьте выбранную копию командой выше. В отдельном закрытом каталоге
восстановите `database.sqlite3`, `code.tar.gz`, `media.tar.gz`, `private.tar.gz`
и `config.tar.gz`; сравните commit и зависимости из `runtime.json`. Настройки
из `config.tar.gz` содержат секреты — права доступа должны остаться закрытыми.
Создайте отдельное окружение Python, выполните `check`, `migrate --check`,
`collectstatic` и проверку приложения с восстановленной копией, без подключения
к рабочей базе. Автоматическая проверка архивов не заменяет эту проверку
полного восстановления приложения.

Заменять рабочую базу можно только после отдельного согласования потери данных,
созданных после выбранной копии, и новой резервной копии текущего состояния.
Останавливать и запускать можно только `aya.service`. Telegram Archive и другие
приложения не участвуют в восстановлении AYA. Скрипт копирования никогда сам
не восстанавливает production-базу и не запускает миграции.

Копии на том же VPS **не защищают от потери всего сервера**. Внешнего хранилища
пока нет; после его подключения нужны зашифрованная передача и отдельная
проверка восстановления скачанной копии. Доставка уведомлений о сбое вне VPS
также не настроена: результат доступен в systemd journal.
