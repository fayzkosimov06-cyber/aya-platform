# Изоляция AYA

Веб-приложение работает от системного пользователя `aya-web`, без входа по SSH
и без sudo. Оператор развёртывания остаётся отдельным пользователем `deploy`;
его полномочия для других проектов не меняются.

`aya.service` сохраняет адрес `127.0.0.1:8001` и три процесса Gunicorn. Nginx
менять не требуется. `NoNewPrivileges`, пустой набор capabilities, ограничения
пространств имён, закрытый домашний каталог и доступ только для чтения к коду
задают границы веб-службы. Писать можно только в `var`, `media`, `private` и
её временный каталог. Git-метаданные и файл окружения внутри службы недоступны;
окружение передаёт системный менеджер systemd.

SQLite находится в `/srv/aya/var/db.sqlite3`, путь задаёт `AYA_DB_PATH`.
Корневой каталог проекта остаётся недоступным для записи веб-пользователю.
Не создавайте ссылку `db.sqlite3` на новую базу: все команды обслуживания
должны получать тот же `AYA_DB_PATH`, иначе можно случайно использовать старую
базу. Резервная служба получает значение через `/etc/aya.env`.

Группа `aya-data` даёт фоновой службе копирования доступ к данным. Она включена
в `SupplementaryGroups` только `aya-backup.service`; глобальные группы
пользователя deploy и других приложений не меняются. Закрытые файлы карт имеют
права 0640, каталоги 2750 внутри закрытого корня. Публичные медиа имеют права,
разрешающие чтение Nginx. Секреты `/etc/aya.env` доступны root и deploy (0640),
но не другим пользователям. Production-настройки читаются веб-пользователем
через группу aya-data (0640).

## Фотографии

Новые фотографии профиля ограничены 5 МБ и 20 миллионами пикселей, сохраняются
в JPEG до 1600 × 1600 и до 1 МБ без исходных метаданных. Проверки выполняются
в модели, включая Django Admin и прямое сохранение модели. Существующие фото
не перекодируются при редактировании других полей.

По умолчанию разрешено 10 замен за час, 30 за сутки, до 64 МБ истории одного
аккаунта и до 2 ГБ общего хранилища аватаров/истории. Сохраняется резерв 1 ГБ
свободного диска. Значения `PROFILE_PHOTO_*` можно определить в production-
настройках при необходимости. Нарушение лимита показывает ошибку поля.

После успешной транзакции старое фото переносится в закрытый
`private/avatar_history`, если на него больше не ссылается ни одно файловое
поле моделей. Байты и контрольная сумма сохраняются, создаётся запись
восстановления. Рабочие материалы и фотографии карт сохраняются.

Команда `archive_profile_photos` показывает количество старых неиспользуемых
файлов без вывода имён. `--apply` переносит их в архив, не удаляя содержимое.
Сначала нужна свежая проверенная копия. `--restore НОМЕР --apply` возвращает
файл по закрытой архивной записи после проверки пути и контрольной суммы,
если исходное место свободно. Автоматического уничтожения истории нет;
при достижении квоты требуется отдельное решение владельца о хранении.

## Проверка и откат

Перед переключением сохраняются база, медиа, закрытые файлы, окружение,
unit-файлы, права/владельцы файлов и Python-окружение. Переключение базы
выполняется при остановленной только AYA, с проверкой всех таблиц. Схема и
пользовательские записи не меняются. Старый файл базы сохраняется закрытым
до завершения проверки. Миграций этой версии нет.

Если откат нужен после запуска пользователей, нельзя подменять новую рабочую
базу старой копией: откатываются код и зависимости, а актуальная база остаётся
в `var` с соответствующим `AYA_DB_PATH`. Systemd пользователь/права должны
соответствовать выбранной конфигурации. Остальные приложения не участвуют.
